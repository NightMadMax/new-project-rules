# Работа через EDT

## Приоритет маршрута

EDT-маршрут — основной. Метаданные, модули, поиск, валидация и список ошибок
берутся из EDT-проекта, а канон исходников в репозитории — EDT-формат.

XML-маршрут допускается, только когда задача в EDT не решается. Порядок:

1. Назвать, что именно не решается в EDT.
2. **Предупредить пользователя явно:** конвертация в XML и обратно — не
   бесплатная операция. На больших конфигурациях она заметна по времени,
   обратное преобразование может терять нюансы, а обновление EDT мигрирует
   формат и даёт diff без содержательных изменений.
3. Дождаться подтверждения.
4. Выполнить конвертацию детерминированно, показать diff после возврата в
   канонический формат.

Правило действует и для skills: инструмент, работающий только с XML, не
запускается молча.

## Доработка расширением по умолчанию

Режим поддержки читается из колонки `support_mode` реестра баз, а не
предполагается. Изменение конфигурации на поддержке делается расширением. Снятие с поддержки
или правка типовой — отдельное решение пользователя, названное словами, с
записью причины.

## Документация вместо догадок

Поведение платформы уточняется по документации и справке (MCP-роли `help`,
`ssl`, `syntax`), а не подбирается пробами на базе. Проба на живой базе — это
операция с последствиями, у неё свои гейты.

## Результат

Изменение в исходниках под git, прошедшая валидация BSL, названные затронутые
объекты. Правки, сделанные в обход EDT, указываются явно.
