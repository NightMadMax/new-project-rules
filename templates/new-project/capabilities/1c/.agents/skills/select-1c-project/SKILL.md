# Выбор базы для сессии

Скрипты стандарта живут в чекауте `new-project-rules`, а не в проекте, и путь к
нему в проекте не записан. Первый шаг — спросить у пользователя путь к чекауту.
Команды ниже выполняются оттуда, `--root` указывает на проект.

Порт сам по себе не говорит, какая база за ним стоит: runtime-клиент можно
перезапустить на другую базу, а конфигурация порта останется прежней. Поэтому
выбор всегда подтверждается ответом самой базы.

## Правила

1. **Единственный источник истины — реестр.** База берётся из
   `config/1c-projects.tsv`. Базы, которой нет в реестре, для skills не
   существует: сначала `add-1c-base`.
2. **Выбор подтверждается фактическим вызовом.** После выбора выполняется
   вызов, возвращающий идентификацию базы, и ответ сверяется с реестром. Без
   совпадения работа не начинается.
3. **Session lock.** Подтверждённая база фиксируется на сессию. Lock
   аннулируется при ошибке соединения, при повторном выборе, при перезапуске
   runtime-клиента и при смене порта. Аннулированный lock восстанавливается
   только повторным подтверждением по правилу 2, а не памятью о прошлом ответе.
4. **Обновление конфигурации.** Проверяется до старта и после него. Если
   безопасный запуск без обновления не подтверждён, работа прекращается.
5. **Режим записи подтверждается, а не предполагается.** На обычном приложении
   режим `analysis` обеспечен самой сборкой обработки: чтение технически не
   может записать, и сборки различаются по SHA-256. На управляемом приложении
   такого барьера нет — режим задаёт переключатель в UI, поэтому его фактическое
   состояние читается вызовом и записывается в lock вместе с идентичностью базы.

   Это не пожелание, а предусловие исполнителя. Прочитанное состояние
   передаётся отдельным аргументом — ровно `on` или `off`, — а текст вызова и
   его ответа идёт вторым: одно поле не может нести одновременно факт и его
   доказательство. Предположение по имени файла обработки подтверждением не
   считается.

## Команды

Lock ставится и проверяется вызовом, а не описанием:

```sh
python3 scripts/one_c_session.py --root <проект> acquire \
  --base <project_id>/<environment_id> \
  --confirmed-by "<вызов и что он ответил>" \
  --switch-read off --switch-confirmed "<вызов, прочитавший переключатель>"
python3 scripts/one_c_session.py --root <проект> require --base <project_id>/<environment_id>
python3 scripts/one_c_session.py --root <проект> release
```

`--switch-read` и `--switch-confirmed` нужны только управляемому приложению: у
обычного барьер в самой сборке. Для операции записи к `acquire` добавляются
`--write-mode approved-write` и `--backup-confirmed "<копия и её дата>"`, а
проверяющий вызов — `require --write`. Отказ печатается с пометкой `[REFUSED]`
и ненулевым кодом возврата; работа с базой после отказа не начинается.

## Production

База с `is_production = true` не выбирается неявно. Требуется отдельное
подтверждение пользователя в текущем диалоге, названное словами: какая база,
какой контур, зачем. Совпадения по имени, порту или «последней использованной»
недостаточно.

## Платформа

Операции с живой базой выполняются только на Windows: на другой ОС исполнитель
`scripts/one_c_session.py` отказывает по действующему lock и называет причину.
Всё остальное — репозиторий, документация, ревью, валидаторы и сборка проекций
— работает на любой ОС, поэтому подготовить и проверить работу можно где угодно,
а выполнить — на Windows.

## Режим записи

По умолчанию lock берётся в режиме `analysis`. Режим `approved-write`
запрашивается отдельно и требует двух вещей сразу: контур не production и
названная резервная копия — какая и когда снята. Исполнитель
`scripts/one_c_session.py` отказывает без неё и отказывает на production
независимо от подтверждения выбора.

## Результат

Названы: `project_id`/`environment_id`, контур, порт, `application_kind`,
признак production, чем подтверждена идентификация, режим записи и —
для `approved-write` — подтверждённая копия. Это состояние session lock
для последующих skills.
