# Настройка окружения 1С

Установка — действие с последствиями вне репозитория, поэтому skill сначала
показывает, что именно предлагает поставить, и ждёт подтверждения.

Скрипты стандарта живут в чекауте `new-project-rules`, а не в проекте. Первый
шаг — спросить у пользователя путь к чекауту; команды выполняются оттуда,
`--root` указывает на проект.

## Порядок

1. Выполнить `doctor-1c` и показать отчёт. Он определяет объём работ.
2. Показать каталог компонентов:

   ```sh
   python3 scripts/one_c_setup.py --root <проект>
   ```

   Отчёт даёт по каждому компоненту состояние (`found` / `missing` / `n/a`) и
   prompt: назначение, включаемые функции, класс, последствия отказа, версия,
   источник, документация, способ установки, требования admin, restart, сети,
   учётных данных и лицензии, а также три варианта ответа. Prompt приходит из
   `config/1c-components.tsv` целиком: пересказывать его короче нельзя — поля,
   которые кажутся лишними, и есть то, на чём стоит решение.
3. Получить явный ответ пользователя по каждому компоненту и записать их в
   JSON-файл вида `{"<компонент>": "<выбранный вариант>"}`.
4. Применить только записанное:

   ```sh
   python3 scripts/one_c_setup.py --root <проект> --apply decisions.json
   ```

   Исполнитель запускает команду только для варианта «установить
   автоматически» и только ту, которую объявил каталог. Компонент без ответа
   остаётся нетронутым. После установки состояние перепроверяется фактически:
   «команда завершилась успешно» результатом не считается.
5. Записать фактические версии в `docs/operations/TOOLCHAIN.md`. Документ
   принадлежит проекту: заполняется по факту, а не по намерению.
6. Настроить EDT по `docs/operations/EDT_SETUP.md`.
7. Собрать клиентские проекции: `activate-1c-client`.
8. Повторно выполнить `doctor-1c`. Отчёт после — часть результата.

## Классы компонентов

Пропуск `required` даёт итог `incomplete`. Пропуск `conditional` перечисляет
отключённые функции, но итог не меняет. Пропуск `optional` не влияет ни на что.
Это разные последствия, и сводить их к «чего-то не хватает» нельзя.

## Внешний MCP provider

Provider — чужая поставка. Skill его **обнаруживает**, а не разворачивает:

```sh
python3 scripts/one_c_provider.py --root <проект> --manifest <path>
```

Проверяются identity, health и объявленные инструменты; в клиентские проекции
(`render-1c-clients.* --provider-manifest`) попадает только прошедший проверку
endpoint. Вторые контейнеры не разворачиваются: `docker run`, `compose` и
`start` исполнителю запрещены, разрешены только `ps`, `inspect` и `version`.

## Границы

- Установки в обход штатного установщика и менеджера пакетов нет.
- Живая база не затрагивается: ни создания, ни обновления, ни подключения.
- Репозиторий в транзакцию не входит: исполнитель ничего не пишет внутрь
  проекта, поэтому отказ установки не повреждает готовый репозиторий.
- Секреты не записываются в репозиторий. `.dev.env` не отслеживается git —
  это уже учтено в `.gitignore` проекта.
