# Разработка на 1С

Этот файл — маршрутизатор. Он не повторяет правила, а называет reference, в
котором они живут. Загружать нужно только то, что относится к текущей задаче:
подгрузка всего набора «на всякий случай» съедает контекст и не улучшает
результат.

## Что делается до первой строки кода

1. **Проверить метаданные, а не вспомнить их.** Имена реквизитов, табличных
   частей и объектов берутся из фактической конфигурации через MCP-поиск.
   Придуманное имя — дефект, который найдётся на этапе компиляции в лучшем
   случае и в проде в худшем.
2. **Поискать готовое.** Экспортные методы общих модулей и модулей менеджеров,
   шаблоны, механизмы БСП и самой платформы (криптография, полнотекстовый поиск,
   регулярные выражения, очереди) проверяются до проектирования своего решения.
   Найденный механизм используется, а не дублируется параллельной реализацией.
3. **Определить маршрут изменения.** Конфигурация на поддержке дорабатывается
   расширением — см. [`references/extensions.md`](references/extensions.md).

## Гейты, которые не обходятся

- Мутация `Form.xml` и разметки идёт через skill `1c-metadata-manage`, а не
  правкой XML руками. Логика в `Form.Module.bsl` — обычная работа с BSL и под
  этот гейт не попадает.
- Работа с фактической базой требует действующего session lock — см.
  `select-1c-project`.
- Production требует отдельного явного разрешения; ни один reference этого
  правила не ослабляет.

## Отношение к upstream

References адаптированы из правил внешнего источника и являются каноном для
этого проекта. Пошаговые инструкции по инструментам не дублируются: они
поставлены побайтно в `.agents/skills/1c-metadata-manage/docs/` и
`.agents/skills/mcp-1c-tools/docs/`, и references ссылаются на них. Когда
инструкция и reference расходятся, правило принадлежит reference, а порядок
вызова инструмента — доставленному документу.
