# Настройка EDT

Порядок установки и то, что проверяет `doctor-1c`. Машинозависимые значения
(пути, идентификаторы, alias баз) сюда не записываются: их резолвит текущий
workspace EDT.

## Порядок

1. Платформа 1С нужной ветки.
2. Стабильная EDT 2026.x. Java и плагин 1С:Напарника входят в поставку.
3. Совместимый EDT-MCP; совместимая пара фиксируется release capability.
4. Токен Напарника в локальном runtime state, не в Git.
5. Плагин обычного приложения — только для баз `application_kind = ordinary`.
6. Патч `Run without update` — только если эта функция выбрана.
7. Профили запуска из шаблонов capability.

## Профили запуска

Обработка Toolkit одна — `configurations/toolkit/MCP_Toolkit_Ordinary.epf`.
Профилей запуска может быть несколько, но различаются они только параметрами
`/C "startup;…"` в `ATTR_STARTUP_OPTION`: `write=1` включает авторазрешение
записи, `privileged=1` — привилегированный режим. Отдельно идёт отладочный
профиль: он не запускает обработку и в счёт Toolkit не входит. Все для
обычного приложения.

| Профиль | Параметры запуска |
|---|---|
| `Запуск Toolkit (только чтение)` | `write=0;privileged=0` |
| `Запуск Toolkit` | `write=1;privileged=0` |
| `Запуск Toolkit (привилегированный)` | `write=1;privileged=1` |
| `1С — обычное приложение (HTTP debug)` | только клиент, без `/Execute` |

**Обработка лежит в проекте**, рядом с профилями, которые её запускают:
`configurations/toolkit/`. Абсолютный путь к рабочему столу делал профиль
личным — он работал на одной машине и называл каталог, которого нет ни у кого
другого.

Обработка подключается **клиентом** к общему прокси на `127.0.0.1:6003` и
объявляет канал своей базы; свой HTTP-сервер она не поднимает. Заголовок формы
показывает адрес прокси, канал и режим — это и есть подтверждение того, что
запущено.

`write=0` — это режим интерфейса, а не технический барьер: опасные операции
ограничиваются флагами подтверждения на стороне прокси, а не самой обработкой.
Режим только-чтение как гарантию даёт настройка Docker-контейнера прокси, не
файл EPF.

Для `application_kind = managed` собственной обработки нет: там барьер записи —
переключатель в UI Toolkit, и режим подтверждается вызовом, а не файлом.

Переносимы только имена профилей и критические атрибуты. Идентификаторы
приложения, runtime UUID и пути остаются плейсхолдерами и резолвятся EDT.

Поэтому профили поставляются как `seed`: они создаются один раз и дальше
принадлежат проекту. Плейсхолдер `<EDT_PROJECT>` подставить некому — имя
проекта в workspace знает только пользователь, — а EDT переписывает `.launch`
при первом сохранении конфигурации запуска в UI. Будь они `managed`, первая же
такая правка стала бы дрейфом и остановила обновление всей capability.

Профиль Toolkit несёт ещё три плейсхолдера, и заполняет их тоже пользователь:

| Плейсхолдер | Чем заменить |
|---|---|
| `<TOOLKIT_EPF>` | путь к собранной обработке Toolkit |
| `<TOOLKIT_PROXY_URL>` | адрес прокси, обычно `http://127.0.0.1:6003` |
| `<TOOLKIT_CHANNEL>` | канал базы — тот же, что в колонке `toolkit_channel` реестра |

Канал обязан совпадать с реестром: разойдутся — MCP-клиент получит таймаут, а не
внятную ошибку, потому что прокси ответит, а за каналом никого не окажется.

У профиля `ordinary` обязателен атрибут `ATTR_CLIENT_TYPE`: без него база
стартует не тем клиентом, а сам факт наличия файла профиля об этом ничего не
говорит. `doctor-1c` проверяет атрибут и только у строк `ordinary`.

## Что записывается в `.dev.env`

Часть компонентов не сообщает о себе машине: плагин и патч живут внутри
установки EDT, токен — в чужом сервисе, manifest провайдера — за пределами
репозитория. Обходить профиль пользователя ради них диагностика не будет, а
придумывать версию, которой никто не измерял, нельзя, — поэтому состояние
записывается сюда и читается отсюда.

| Ключ | Что записывается | Кто читает |
|---|---|---|
| `EDT_MCP_VERSION` | версия установленного EDT-MCP | `doctor-1c` |
| `EDT_ORDINARY_PLUGIN` | версия плагина обычного приложения | `doctor-1c`, только для `ordinary` |
| `EDT_RUN_WITHOUT_UPDATE` | версия патча `Run without update` | `doctor-1c` |
| `YAXUNIT_EXTENSION` | версия установленного расширения тестов | `setup-1c-environment` |
| `NAPARNIK_TOKEN` | токен 1С:Напарника | `setup-1c-environment` |
| `MCP_PROVIDER_MANIFEST` | путь к manifest внешнего MCP provider | обнаружение провайдера |

Пустой ключ означает «не записано», а не «не установлено»; отчёт называет
именно это различие. Значения не выводятся: в отчёт идёт имя ключа и признак
«задан».

Образцов два, и это не дублирование: `.dev.env.example` приходит из upstream
побайтно и описывает параметры его инструментов, `.dev.env.standard.example`
несёт ключи из таблицы выше. Дописать наши ключи в upstream-файл нельзя, не
сломав его побайтность, поэтому `.dev.env` собирается копированием обоих
образцов в один файл.
