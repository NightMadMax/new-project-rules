замыслу: каждая находка ниже воспроизведена на созданном проекте, на живом

главный вывод, а не список ниже.

## Блокирующее

Заведено дефектами №242–№244.

### 1. `apply-capability-artifacts --apply --yes` делает проект невалидным

Воспроизведено на проекте профиля `software` без capability и документированной
команде из `docs/guides/MANUAL_SCRIPTS.md`:

```
Applied.
[ERROR] capability.removed .project-standard.json: Capability 'jira-confluence'
        installed artifacts recorded in the ledger but is missing from metadata.
```

19 файлов записаны, ledger обновлён, а `.project-standard.json`, `INDEX.md`,
`docs/README.md` и `.best-practices.json` не тронуты: вторую половину установки
делает только bootstrap (`bootstrap-new-project.sh:214`). Для `1c` добавится
`capability.stack_missing`, а `check_capabilities` (`validate-project.py:744`)
потребует wikilinks, которых никто не поставит.

Текст отказа описывает противоположное произошедшему: пользователь добавил
capability штатным инструментом, а ему сообщают, что он её удалил и должен
пересоздать проект. Восстановление — только правкой metadata руками.

Сценарий объявлен поддержанным: `capability_artifacts.py:174` объясняет ветку
подстановки именно тем, что отказ означал бы «capability можно выбрать только
при создании».

### 2. Session lock не имеет исполнителя

`scripts/one_c_session.py` не импортируется ничем, кроме собственного теста: ни
скриптом, ни обёрткой, ни CLI (`__main__` отсутствует), ни одним `SKILL.md`.
Единственное упоминание `.1c-state` во всей поставке — строка в
`appendix/gitignore`.

Модуль открывается словами «правило без исполнителя — правило, которому
следующая сессия может и не последовать. Это исполнитель». Замок, решающий,
можно ли писать в живую базу, и отдельно запрещающий запись в production,
недостижим из рабочего пути.

`READINESS_1C.md` держит критерий 8 — «Live-base skill отказывается без session
lock» — в статусе `тест` с доказательством `test-1c-session.py`. Тест грузит
модуль напрямую и ни одного скилла не запускает: критерий сформулирован про
связь, а проверяется сторона связи, которой не с чем соединяться.

### 3. `capability_releases` не заполняется никогда

Проект, созданный `--preset 1c` из release `0.6.0` с непустым `release_id`:

```json
"capabilities": ["1c"],
"capability_releases": {},
```

Поле валидируется в `project_metadata.py`, вставляется пустым миграцией 0013,
пишется пустым обоими bootstrap — и не заполняется ничем. На нём держатся три
утверждения: `ARCHITECTURE.md:56` («обновление определяется сравнением
`release_id`»), критерий приёмки Э6 («снятие ядра capability обнаруживается по
записи release в metadata») и дефект №148 («запись release считается
доказательством принадлежности»).

Фактически принадлежность ловит ledger, а сравнения `release_id` не происходит
нигде: план строится побайтовым сравнением файлов. Долг признан в
`one-c/IMPLEMENTATION_PLAN.md:181`, но три документа выше описывают механизм как
действующий, и критерий приёмки этапа считается выполненным.

## Важное

Заведено дефектами №245–№251.

### Проверки, зелёные при любой реализации

- `test-1c-readiness.py` сверяет матрицу с мастер-планом и наличие файла теста.
  Совпадение критерия с кодом не проверяется — отсюда находка 2.
- `test-check-skills.py:569`: `PHANTOM_FLAGS = ("--include-memory",
  "--mode install")`. Комментарий объявляет инвариант «скилл не называет флаг,
  которого нет в скрипте»; реализован блоклист из двух найденных случаев.
- Там же `CHECKOUT_CAVEAT`: достаточно, чтобы литерал `new-project-rules`
  встретился где угодно в файле.
- `CAPABILITY_NAMES` (`project_metadata.py:28`) — хардкод, ни с чем не
  сверяемый, в отличие от соседнего `CAPABILITY_CORE`, у которого сверка с
  манифестом есть. Bootstrap принимает capability по манифесту, валидатор — по
  этому множеству.

### Писатель, который не проверяет то, что пишет

`one_c_clients.py:301` отвергает URL с кавычкой или переводом строки и
объясняет это правильно: писатель, который не может выразить значение, обязан
отказать. Имя сервера собирается из `project_id`/`environment_id` того же
`config/1c-projects.tsv` — seed, который заполняет человек, — и не проверяется.
Воспроизведено:

```toml
[mcp_servers.onec_toolkit_erp.a"_dev]
url = "http://127.0.0.1:6003/mcp"
```

Невалидный TOML, после которого Codex не прочитает и пользовательскую часть
`config.toml` за пределами маркеров. Правило существует — `ONE_C_ID_RE` в
`validate-project.py:417`, — но живёт в валидаторе, а `render-1c-clients.py`
запускается отдельно и валидатор не вызывает.

### Паритет bootstrap

`bootstrap-new-project.ps1:159` для строк `capabilities.tsv` проверяет
небезопасный destination и конфликт с артефактом профиля. `bootstrap-new-project.sh:200`
для тех же строк проверяет только наличие шаблона и класс payload; проверка
`..` и `//` применяется лишь к `profiles.tsv`. Parity-тесты сравнивают
полученные деревья и увидеть эту разницу не могут: при здоровом манифесте выход
одинаковый.

Ни одна из реализаций не ловит две capability с одним destination (сейчас таких
нет); `capability_artifacts` ловит дубль только внутри одной capability.

### Мёртвый барьер

`capability_artifacts.py:162`:

```python
if parent.exists() and parent.resolve() != (project_root / target).parent.absolute().resolve():
```

Обе стороны — одно выражение: `parent` и есть `(project_root / target).parent`,
а `.absolute().resolve()` равно `.resolve()`. Проверено на symlink наружу:
строка 162 — `False`, строка 164 — `True`. Работает один барьер из двух внешне
независимых, с одинаковым текстом ошибки.

Рядом: `ledger_document` записывает rendered managed-артефакт с `policy: "seed"`,
решая это сравнением строки `detail == "rendered by bootstrap"`
(`capability_artifacts.py:406`). Ветка сейчас недостижима — в манифесте нет
managed-строк с плейсхолдерами, — но решение по человекочитаемому полю осталось.

- 240 из 264 строк `capabilities.tsv`, 8.3 МБ из 8.4 МБ payload, 27 из 107

- `ARCHITECTURE.md` описывает слой доставки и не описывает runtime: session,

- `CHANGELOG.md` — 59 КБ при пороге 32 КБ; `compress-project` сообщает, что
  политика `--changelog-keep 5` не даёт уменьшить дальше: порог и политика
  противоречат друг другу. 8 исправленных дефектов ждут архивации.
- Ревью от 2026-08-01 не было внесено ни в `INDEX.md`, ни в `docs/README.md`.

## Что держит систему

Не комплименты — то, без чего находки выше были бы блокирующими.

- `capability_artifacts` проверен на живом проекте: 240 `adopt` → `up_to_date` →
  0 ошибок валидатора. Транзакция, остановка на дрейфе, однократный seed,
  владение по манифесту работают ровно как заявлено. Находка 1 — про то, чего
  этот модуль не делает, а не про то, что он делает.
- Двойной барьер на TOML — провайдер отвергает адрес, писатель отвергает
  повторно — правильная форма; именно поэтому его отсутствие на имени сервера
  является находкой, а не придиркой.
- `release_id` детерминирован, и длины документов подмешаны в digest до
  конкатенации: текст, перенесённый между паспортом и ledger, не даст тот же
  идентификатор.
- CI закрыт по-настоящему: три ОС, обе редакции PowerShell, цикл с
  `$LASTEXITCODE`, `shell: bash` в обязательной cross-repo джобе, таймауты
  везде, парсинг всех 82 `.ps1` включая dot-каталоги. Все находки прошлого
  ревью по CI закрыты и перепроверены.
- Ledger как независимый свидетель сработал в эксперименте — пусть и сообщил не
  о том.
- Раздел `Open` в `DEFECTS.md` был пуст при 241 записи с разбором корневых
  причин.

## Порядок продолжения

1. №242 — либо `apply-capability-artifacts` дописывает metadata, оба индекса и
   стек, либо отказывается на capability, отсутствующей в metadata, с честным
   сообщением. Молчаливое приведение проекта в невалидное состояние — худший из
   трёх вариантов.
2. №243 — либо вызвать `one_c_session` из скиллов живой базы, либо снять
   критерий 8 из зелёных.
3. №244 — заполнять `capability_releases` при доставке либо убрать утверждения
   о нём из трёх документов.
4. №248 — проверка имени сервера рядом с проверкой URL; `ONE_C_ID_RE` в общий
   модуль, как уже сделано с диапазоном портов.
5. №249 — destination capability в `bootstrap-new-project.sh` до паритета с
   `.ps1`; тест на манифест, а не на дерево.
6. Остальное — по журналу дефектов.
