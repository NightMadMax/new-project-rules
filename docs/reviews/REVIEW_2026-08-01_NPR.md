# Ревью всего NPR, 2026-08-01

Пять независимых ревьюеров по разным срезам, ни один не писал проверяемый код:
архитектура целиком, Python в `scripts/`, shell/PowerShell и CI, поставка
`templates/**` с манифестами, собственные скиллы и документация стандарта.
Несколько находок получены двумя-тремя срезами независимо — они помечены.

Все автоматические гейты при этом зелёные: `check_skills`, `validate-project`,
`check_best_practices_contract`, весь Python-набор. То есть **всё найденное
лежит вне зоны действующих проверок** — это главный вывод ревью, а не список
ниже.

## Точка остановки

Работа прервана пользователем на первом исправлении. Ветка
`fix/review-blocking`, в рабочем дереве два незакоммиченных изменения и этот
файл:

- `config/capability-core.tsv` — добавлены строки `jira-confluence software -`
  и `transcribe software -`;
- `scripts/project_metadata.py` — те же две записи в `CAPABILITY_CORE`, а
  `CAPABILITY_REQUIRED_STACK` научился пропускать `-`, иначе прочерк стал бы
  именем обязательного стека.

Пара согласована, но **не проверена ни одним прогоном**: тесты не запускались
по просьбе пользователя. Первое действие при продолжении —
`PYTHONDONTWRITEBYTECODE=1 python scripts/test-preset-core.py`; он сверяет
манифест с константой и упадёт, если пара разошлась.

Исправление закрывает только подъём профиля. Теста на связку
профиль ↔ `docs_section` ещё нет, а без него четвёртая capability повторит
падение с удалением каталога.

## Блокирующее

### 1. `minimal` + `transcribe` или `jira-confluence` роняет bootstrap, и откат удаляет каталог

Поставка. Capability с непустым `docs_section` требует `docs/README.md`, а тот
появляется с профиля `software`. В `config/capability-core.tsv` строка была
только для `1c`, поэтому профиль не поднимался. Все файлы записываются, шаг
индексации падает (`ensure_docs_index_entry`, `bootstrap-new-project.sh:483`),
срабатывает `cleanup_failed_bootstrap` → `rm -rf` каталога назначения.
`.agents/skills/create-new-project/SKILL.md:25` прямо предлагает `minimal`.

Исправление начато (см. «Точка остановки»). Нужен ещё тест на связку
профиль ↔ `docs_section`, иначе четвёртая capability повторит это.

### 2. Инъекция в `.codex/config.toml` через provider manifest

Python. `one_c_provider.py:116,211,229`: проверяется `entry["health"]`, а
регистрируется `entry["url"]` — разные поля, и `url` не валидируется. Дальше
`one_c_clients.py:293` собирает TOML конкатенацией без экранирования.
Воспроизведено: manifest с валидным `health` и `url`, содержащим кавычку и
перевод строки, проходит со статусом `OK` и дописывает в конфиг Codex секцию
`[mcp_servers.evil]` с произвольной командой.

Исправление: проверять и регистрировать один адрес; отклонять `url` с `"`,
`\`, CR, LF; тест на расхождение `health`/`url` — сейчас ни одна фикстура не
задаёт их по-разному, поэтому мутация не ловится.

### 3. `jira-confluence`: заполняемые документы помечены `managed`

Архитектура и поставка независимо. `config/capabilities.tsv:2–12` — 11
документов-бланков (`JIRA.md`, `CONFLUENCE.md`, модели статусов, каталог
запросов) с `policy = managed`. Пользователь заполняет файл — то есть делает
то, ради чего файл поставлен — и следующее обновление capability встаёт с
конфликтом на **все 17 артефактов**, включая скиллы: конфликты собираются на
весь план (`capability_artifacts.py:224`).

У `1c` и `transcribe` такие же по природе документы размечены `seed`.
Capability появилась до колонки `policy` и была проставлена `managed` целиком.

Исправление: перевести 11 строк в `seed`. Отдельно — инвариант «строка
`template`+`managed` без плейсхолдеров, целью которой является Markdown в корне
или `docs/`, подозрительна»: сегодня это единственный класс ошибки, который не
проявляется до первого обновления у пользователя.

### 4. Два несовместимых словаря ключей `.dev.env`

Архитектура и поставка независимо. В проект доставляется только
`upstream/.dev.env.example` (`capabilities.tsv:218`) с ключами
`PLATFORM_PATH`, `IB_USER`, `IB_PASSWORD`. Наш
`templates/new-project/capabilities/1c/dev.env.template` с ключами
`EDT_MCP_VERSION`, `EDT_ORDINARY_PLUGIN`, `MCP_PROVIDER_MANIFEST`
**не объявлен ни одной строкой манифеста** и в проект не попадает.

Пользователь копирует полученный образец, заполняет — и `doctor-1c` сообщает,
что `EDT_MCP_VERSION` не записан. `scripts/test-1c-setup.py:140` называет
недоставляемый файл «shipped .dev.env template» и потому зелёный.

Исправление: выбрать один канон — либо доставлять наш шаблон отдельной строкой,
либо внести наши ключи в upstream-файл через `config/1c-adaptations/`
(механизм есть и уже применён к трём файлам с двумя писателями). Тест
переориентировать на манифест, а не на файл в чекауте.

### 5. `cross-repo-e2e` на Windows не умеет краснеть

CI. `.github/workflows/ci.yml:193-198` — две команды в одном многострочном
`run`, shell `pwsh -command` без построчной проверки: возвращается код
последней. Падение `check_best_practices_contract.py` невидимо. Джоба —
обязательная проверка ruleset, то есть защита ветки опирается на шаг, который
не краснеет. В этом же файле ловушка уже описана и обойдена циклом с
`$LASTEXITCODE` (строки 98–100) — здесь обход не применён.

## Важное

- `one_c_doctor.occupied()` на Windows не видит слушателя на `0.0.0.0`
  (проверено: `127.0.0.1` → `True`, `0.0.0.0` → `False`). Промахивается ровно
  мимо платформы 1С на `6003` — случая, ради которого написана. Тест биндит

- Профили запуска EDT (`capabilities.tsv:22-23`) — `managed` с плейсхолдерами
  `<EDT_PROJECT>`, `<RUNTIME_INSTALLATION>`, которые bootstrap не подставляет.
  EDT такой профиль не запустит; пользователь правит — конфликт на ~230
  артефактов capability `1c`.

  одним предложенным ответом: ветка «подтверждено человеком» ждёт ответа

  На настроенной машине `setup-1c-environment` никогда не даст `ready`.

## Что держит систему

Не комплименты — то, без чего находки выше были бы блокирующими.

- `capability_artifacts.py`: дрейф — остановка, а не перезапись; seed
  создаётся один раз; владение объявлено манифестом, а не угадывается; apply
  транзакционный с откатом. Находка №3 — ошибка данных, а не архитектуры:
  механизм отработает правильно, просто скажет «нет» там, где должен сказать
  «твоё».
- Ledger как второй независимый свидетель против metadata: ручное удаление
  capability ловится сравнением того, что записала транзакция, с тем, что
  человек мог отредактировать.
- `one_c_clients.py` — владение по имени: всё, что не `onec-*`, переживает
  любой рендер. Сосуществование двух писателей решено, а не запрещено.
- Оба bootstrap читают манифест напрямую, и это доказано parity-тестами в
  изолированной копии, а не заявлено.
- Матрица готовности, сверяемая машинно с планом.
- Раздел `Open` в `DEFECTS.md` пуст не потому, что туда не пишут: 199 записей с
  разбором корневых причин.
