# Capability `1c`: план реализации

Рабочая последовательность для принятых
[[docs/architecture/ONE_C_CAPABILITY_PLAN|мастер-плана]],
[[docs/architecture/one-c/DELIVERY_AND_STATE_PLAN|подплана доставки]] и
[[docs/architecture/one-c/ENVIRONMENT_SETUP_PLAN|подплана среды]]. Здесь порядок
работ, приёмка и ревью; решения не пересматриваются — расхождение реализации с
планом заводится дефектом.

Этапы пронумерованы **в порядке выполнения**. Порядок выбран так, чтобы каждый
следующий этап опирался на уже проверенный контракт, а самый дешёвый шёл первым
и обкатал процесс «ветка → PR → ревью».

## Правила работы

- Один этап — одна ветка `feat/1c-<этап>`; в `main` попадает завершённый этап,
  а не промежуточное состояние. Вливание — обычным pull request с прохождением
  required checks: admin-bypass ruleset `Protect main` остаётся исключением
  только для выпуска release capability (решение 1.25) и на код этапов не
  распространяется. До 2026-07-30 это правило было невыполнимо: ruleset требовал
  approval, которого единственный владелец репозитория выдать себе не может, и
  все этапы вливались обходом (дефект №190). Требование снято, маршрут стал
  исполнимым.
- В той же задаче, что код: тесты, `docs/guides/USE_THIS_PROJECT.md` или
  `MANUAL_SCRIPTS.md`, `INDEX.md`, `CHANGELOG.md`, перенос закрытых дефектов и
  отметка статуса этапа в таблице ниже.
- Каждый скрипт имеет пару shell/PowerShell либо явное обоснование, почему нет;
  parity проверяется тестом.
- Windows-зависимые проверки помечаются `SKIP` на других ОС и выполняются в
  отдельной сессии (веха W).

## Архитектурное ревью после каждого этапа

Ревью — часть этапа, а не необязательное дополнение: PR не вливается, пока оно
не пройдено. Проводится независимым ревьюером (отдельный агент или отдельная
сессия), который **не писал** код этапа, по четырём срезам:

1. **Соответствие решениям.** Каждое изменение сверяется с журналом решений
   мастер-плана: не введён ли контракт, который решение отменило, и не осталось
   ли решение без реализации.
2. **Границы владения.** Кто владеет каждым изменённым файлом и ключом; не
   появилось ли второго канонического источника той же информации; сохраняются
   ли project-seed и user-owned артефакты.
3. **Совместимость и миграции.** Что произойдёт с уже созданным проектом
   предыдущей версии; есть ли путь обновления и обратим ли он; не сломан ли
   повторный bootstrap.
4. **Проверяемость.** Каждое утверждение приёмки подтверждено тестом, а не
   ручным наблюдением; тест падает при откате исправления (паттерн №3 из
   `PLAYBOOK.md`).

Результат ревью: находки уровня «блокирует» правятся до merge; находки уровня
«отложить» заводятся дефектом с обоснованием. Ревью без находок тоже
фиксируется — одной строкой в PR, чтобы был виден факт проверки.

## Этапы

### Э1. Проверки skills

**Выполнен 2026-07-26** (PR #25). Закрывает №129. Зависимостей нет. Размер: S.
Ветка `feat/1c-skills-checks`.

Ревью потребовало вернуться к этапу дважды: список hash вынесен из vendored
subtree в `config/skills-payload/`, добавлена валидация путей и симлинков,
незаявленный skill и осиротевший мост стали ошибкой, сообщения приведены к
одному виду на всех платформах. Побочно найдены и исправлены дефекты №143 и
№144; заведены №145 и №146.

Первый намеренно: не трогает контракты, но выпрямляет проверку, которая иначе
будет мешать всем следующим этапам — сейчас добавление skill требует правки
теста, а vendored payload проверить нечем.

1. `test-skills.sh` и `test-skills.ps1` обходят манифест skills вместо девяти
   хардкод-имён; capability-скиллы попадают в обход.
2. Отдельный класс проверки vendored payload: совпадение hash и отсутствие
   локальных правок, без требования внутреннего `agents/openai.yaml`.

Приёмка: добавление skill не требует правки теста; изменённый байт внутри
vendored subtree роняет проверку; shell и PowerShell дают одинаковый вердикт.

Ревью: не ослаблены ли существующие проверки триады для обычных skills.

### Э2. Состояние и схема

**Выполнен 2026-07-26** (PR #26). Закрывает №123 и №128. Зависит от Э1 только
организационно. Размер: L. Ветка `feat/1c-state-schema`.

Ревью нашло блокирующий дефект: миграция 4 → 5 не добавляла
`capability_releases`, поэтому обновлённый проект переставал проходить
собственную валидацию, а повторный план вставал в `blocked`. Исправлено,
добавлен тест на metadata схемы 4 без нового поля.

Единственный полностью блокирующий этап: без ledger и схемы 5 ни доставка, ни
release не имеют куда записывать состояние.

1. Описать ledger `.project-standard-artifacts.json` в
   [[docs/architecture/PROJECT_STANDARD_SCHEMA]]: поля, `policy`, правило hash
   для `owned-block`, собственная `schema`.
2. Модуль-валидатор ledger по образцу `scripts/project_metadata.py`.
3. `STANDARD_VERSION` 4 → 5; `CAPABILITY_NAMES` дополняется `1c`; краткая
   запись release (версия и `release_id`) в `.project-standard.json`.
4. Строки `config/migrations.tsv` для существующих targets.

Приёмка: проект схемы 4 обновляется до 5 без потери `applied_migrations`;
ledger с неизвестным полем и с несовпадающим hash отвергается; bootstrap пишет
metadata схемы 5; повторный прогон миграции — no-op.

Ревью: не смешаны ли две оси версий (schema стандарта и SemVer capability); что
произойдёт с проектом, созданным до bump, если миграцию не применяли.

Точка остановки: если для ledger потребуется поле, не предусмотренное подпланом
доставки, — это изменение контракта, а не деталь реализации.

### Э3. Классы payload и манифест доставки

**Выполнен 2026-07-26.** Закрывает №124. Зависит от Э2. Размер: M.
Ветка `feat/1c-payload-classes`.

Ревью нашло, что побайтность рушилась не при копировании, а при первом коммите:
генерируемый `.gitattributes` нормализовал payload на `git add`. Также валидатор
не проверял природу источника, поэтому бинарник с классом по умолчанию молча
портился подстановкой. Оба исправлены; `-` заменён явным `template` во всех
строках манифеста.

1. Колонка `payload_class` в `config/capabilities.tsv`; пустое значение —
   `template`, существующие строки `jira-confluence` не меняются.
2. Оба bootstrap-скрипта: подстановка только для `template`, побайтное
   копирование для `verbatim` и `binary`.
3. `validate-project.py` проверяет допустимость класса и соответствие источника.

Приёмка: бинарный артефакт доставляется без повреждения (hash совпадает),
подстановка к нему не применяется, shell и PowerShell дают одинаковый результат,
существующая capability `jira-confluence` ставится как раньше.

Ревью: обратная совместимость манифеста; не появилось ли неявного поведения при
пустом значении колонки.

### Э4. Обработчик `capability_artifacts`

**Выполнен 2026-07-26.** Закрывает №122 и №125. Зависит от Э2, Э3. Размер: L.
Ветка `feat/1c-capability-artifacts`.

Ревью нашло, что владение выводилось эвристикой по байтам источника вместо
объявления в манифесте: `USER-RULES.md` без плейсхолдеров стал бы managed и
перезаписывался, а документ, где плейсхолдер даты встречается как пример в тексте, — наоборот. Теперь
`config/capabilities.tsv` объявляет `policy` (`managed`/`seed`), а шаблон с
плейсхолдерами создаёт только bootstrap: обработчик его записывает, но никогда
не создаёт и не сравнивает — значения для отрисовки известны лишь при создании.

Долг Э6: `capability_releases` в metadata обработчиком не заполняется, потому что
`release_id` появляется вместе с build-time release.

1. Многофайловый план `(target, payload_class, action, installed_hash,
   desired_hash, owner)` без записи на диск.
2. Транзакционное применение с откатом всей цепочки; дрейф останавливает
   транзакцию.
3. Удаление managed target только при совпадении hash; seed и user-owned не
   трогаются.
4. Версия capability сравнивается по `release_id`, а не по schema-цепочке.

Приёмка: план на чистом проекте, no-op на повторе, конфликт при дрейфе, откат
при отказе в середине цепочки, сохранение seed и сторонних ключей в смешанных
файлах.

Ревью: атомарность на практике (что остаётся на диске при аварийном
завершении); согласованность с существующими обработчиками и режимом
`--plan`/`--apply`.

### Э5. Preset и ядро

**Выполнен 2026-07-26.** Закрывает №126 и №127. Зависит от Э2. Размер: M.
Ветка `feat/1c-preset-core`.

Порядок шагов исправлен не переносом валидации, а тем, что bootstrap сам
записывает стеки preset: ядро полно в момент создания проекта, а не после
отдельного ручного шага. Заодно снят однокапабилитный guard — оба bootstrap
принимают список capability.

Ревью нашло, что ядро применялось только через preset: позиционный вызов с
capability создавал заведомо невалидный проект. Теперь ядро объявлено в
`config/capability-core.tsv` и следует за capability любым путём выбора.

Не выполнено: приёмочный пункт «снятие ядра невозможно ни правкой metadata, ни
миграцией». Удаление capability из metadata сейчас необнаружимо — признак
принадлежности проекта появится только с записью release в Э6. Заведён
дефект №148, пункт перенесён в приёмку Э6.

1. `config/presets.tsv` и резолвинг preset в обоих bootstrap до записи metadata.
2. `PROFILE_RANKS` выносится в общий модуль; инвариант «`1c` в capabilities ⇒
   профиль ≥ `operated`» в `project_metadata.py`.
3. `validate-project.py` читает `.best-practices.json`; признак ядра —
   `sections["1c"] != "optout"`.
4. В `create-new-project` шаг Best Practices выполняется до валидации; для
   preset `1c` выбор стека безусловен.

Приёмка: понижение профиля, `optout` по секции `1c` и неизвестный preset
отклоняются валидатором; ядро следует за capability при любом способе выбора;
раскрытие preset совпадает в shell и PowerShell. Пункт про невозможность снять
ядро перенесён в Э6 (дефект №148).

Ревью: не сломан ли сценарий создания проекта без доступа к базе Best Practices;
не стала ли проверка ядра блокировать не-1С проекты.

### Э6. Build-time release capability

**Выполнен частично 2026-07-26.** Зависит от Э2, Э4. Размер: L.
Ветка `feat/1c-release-build`.

Сделаны формат и инструменты: паспорт `config/1c-release.json` (зависимости,
MCP-роли, hashes бинарных артефактов), ledger `config/1c-artifacts.tsv` с
колонкой источника, детерминированный `release_id`, offline-сборка против
локального staging с проверкой pinned commit и чистого дерева, weekly-проверка,
которая только уведомляет.

Ревью показало, что дефект №148 я сначала закрыл косметически — поменял текст
сообщения, не изменив поведение. Настоящее исправление опирается на независимый
источник: ledger доставки, который пользователь руками не пишет.

**Сделано 2026-07-30:** гейт `practices/1c` и три исхода сборки (№174, №150);
маршрутизация upstream. `config/1c-routing.tsv` даёт по строке на группу файлов
со ссылкой на решение S.x, `config/1c-upstream-inventory.txt` фиксирует список
tracked-файлов на закреплённом commit `1b6e2ed`, `import_1c_upstream.py`
разворачивает маршруты в строки ledger по локальному чекауту. Покрытие полное:
241 файл, 254 строки (у 13 agents две клиентские проекции), ни одного файла без
маршрута и ни одного маршрута без файла — и то и другое ошибка, потому что
«не упомянут» и «сознательно исключён» в diff через год неотличимы.

Генератор agent-проекций готов (`scripts/one_c_agents.py`, Э8 п.2): 26 строк
несут хэш того, что будет записано. Спецификация преобразования не переписана, а
читается из upstream-адаптеров — `.codex/agents/*.toml` собирается по их шаблону,
`.claude/agents/*.md` сохраняет названный набор полей с одним переименованием.
Повторение спецификации у себя завело бы второй канон, расходящийся при первом
же изменении имени поля наверху. Попутно исправлен маршрут двух целевых
адаптеров: они объявлялись производителями `.claude/settings.json` и
`.codex/config.toml`, то есть вторым писателем файлов, которыми владеет renderer
MCP. Адаптер — вход компиляции, а не её выход.

Обе адаптации выполнены (`config/1c-adaptations/`): `grid-guards` добавляет
проверки положительных `cols`/`rows`, включая авторезультат; `memory-fallback`
меняет единственное предложение — при недоступности сервера факт уходит
каноническому владельцу, а не в `memory.md`, критерии которого от недоступности
сервера не ослабляются. Адаптация записана заменами, а не diff: якорь обязан
совпасть **ровно один раз**, иначе сборка останавливается — ноль совпадений
значит, что предложение, против которого писалась правка, исчезло, а два
значит, что якорь неоднозначен.

Первая же адаптация вскрыла дефект №191: хэши брались из рабочей копии, и при
`core.autocrlf=true` тот же upstream-commit давал разный `release_id` на Windows
и на Linux. Теперь везде читается committed blob.

**Release `0.1.0` выпущен 2026-07-30 со статусом `ready`.** Паспорт
`config/1c-release.json` фиксирует оба источника, десять MCP-ролей и классы
зависимостей; ledger `config/1c-artifacts.tsv` — 254 строки на 241 файл.
Повторная сборка из того же входа даёт тот же `release_id`.

Два отказа по дороге были не в данных, а в самих проверках. `--write` сборки
блокировался тем, что сам же и пересчитывает — несовпадением `inventory_count` и
`release_id`, — то есть только что написанный паспорт нельзя было
проштамповать никогда; теперь эти две находки помечены как самоисправляемые и
блокируют проверку, но не запись. И `action` в ledger хранится отдельно от
`action_id`: запись вида `route:project-ignore` в одну колонку схема не читает.

Маршрут выпуска изменился к лучшему: release влит обычным pull request, без
admin-bypass, потому что требование approval снято с ruleset (дефект №190).
Решение 1.25 в этой части больше не нужно.

**Не сделано:** доставка скомпилированных выходов в шаблон проекта — строки
`config/capabilities.tsv` для 13 agent-проекций и OpenSpec. Это критерии 22 и 25
и остаток №172.

1. `config/1c-release.json` и `config/1c-artifacts.tsv`: pinned commits,
   inventory, четыре действия, ownership, targets, dependencies, hashes.
2. Maintainer-only importer pinned `ai_rules_1c`: побайтный перенос принятого
   payload, только согласованные адаптации, детерминированная компиляция
   проекций Codex и Claude.
3. Weekly check — только уведомление о новом upstream commit, без правок кода.
4. Выпуск фиксируется прямым push с записью в `ACTIONS.md` (решение 1.25).

Приёмка: снятие ядра capability обнаруживается по записи release в metadata
(перенесено из Э5, дефект №148); ledger содержит ровно 241 source-запись pinned commit; повторная
сборка из того же входа даёт побайтно одинаковый выход; сборка и фикстуры
работают без сети; release блокируется при пустом `practices/1c` (решение 1.29).

Ревью: воспроизводимость сборки на чистой машине; полнота inventory против
upstream-дерева; отсутствие сетевых обращений в runtime-пути.

Точка остановки: наполнение `practices/1c` — обязательство решения 1.29; без
него этап завершается, но release не выпускается.

### Э7. Каркас проекта

**Выполнен 2026-07-26.** Зависит от Э3, Э4, Э6. Размер: L.
Ветка `feat/1c-project-scaffold`.

Шестнадцать артефактов: семь managed и девять seed. Критерий — владение, а не
техника: managed обновляется стандартом, seed после создания принадлежит
проекту. Документ, который команда обязана заполнить (`TOOLCHAIN.md`,
`TEST_MODEL.md`, `ONE_C_INTEGRATIONS.md`), не может быть managed: первая же
запись превратилась бы в конфликт и остановила все будущие обновления
capability.

Появился механизм capability-appendix: capability дописывает строки в файлы,

1. Корневые артефакты (решение 1.15): `ONE_C_WORKSPACE.md`,

### Э8. Skills и клиентские проекции

**Частично выполнен 2026-07-27.** Зависит от Э6, Э7. Размер: L.
Ветка `feat/1c-skills-and-clients`.

Сделано: восемь capability-native skills и renderer клиентских проекций.
Renderer владеет только тем, что назвал своим — серверами `onec-…` и правилами
`mcp__onec-…`, — поэтому сторонние MCP и пользовательские настройки переживают
любую пересборку, а повторный запуск не меняет ни одного файла.

Две вещи сознательно не выдумываются. Endpoint, который знает только provider
manifest, показывается как `SKIP`: подставленный URL выглядел бы установленным
и отказал бы при первом вызове. Сервер, который не объявил свои инструменты,
получает строгий класс своей области целиком — точность до инструмента
включается автоматически, как только каталог объявит `tools`.

Символические ссылки в дереве отклоняются: их содержимое не измеряется
отпечатком и не показывается в diff, поэтому перенос ссылки нарушил бы правило
«ничего не попадает в канон незамеченным». Отказ честнее молчаливого переноса.

при отказе записи. Только текстом skill проверяются поведенческие правила:

### Э9. Формат исходников и конвертация

**Выполнен 2026-07-27.** Зависит от Э7, Э8. Размер: M.
Ветка `feat/1c-source-format`.

Три свойства делают обход через XML безопасным, и каждое — правило в коде, а не
привычка. Выгрузка живёт в системном временном каталоге и передаётся абсолютным
путём: чтобы рабочее дерево осталось чистым, ни одно ignore-правило не обязано
быть верным. Конвертация проверяется на детерминизм тем же прогоном — без него
diff возврата перестаёт что-либо значить, поэтому расхождение байт это
остановка, а не «примерно то же самое». Возврат в канон отклоняется, если канон
сдвинулся, пока выгрузка была снаружи: иначе он затёр бы работу, сделанную за
это время.

Отпечаток дерева включает путь и длину каждого файла, а не только байты:
переименование — это изменение, а содержимое соседних файлов не должно
склеиваться в одну строку. Порядок обхода фиксирован, потому что файловые
системы возвращают файлы по-разному.

Состояние принадлежит паре «репозиторий + база»: у проекта несколько баз, и
выгрузка одной не должна ни блокировать, ни удалять выгрузку другой. Каждый
временный каталог помечен владельцем, поэтому уборка после прерванного запуска
трогает только свои. Блокировка принадлежит сессии и истекает по времени:
проверка живости процесса непереносима, а на Windows штатный приём для неё
завершает опрошенный процесс.

Замена канона идёт переименованиями, а старый канон удаляется последним
действием: отказ на любом шаге оставляет целое дерево там, где ему положено
быть. `folder` из реестра обязан быть каталогом строго внутри репозитория —
иначе `.` означал бы замену самого репозитория.

Конвертер задаётся снаружи (`--converter`, `--converter-back`,
`--source-option`, `--target-option`): направления разные, это разные команды, а
их фактическая форма ещё не зафиксирована — дефект №166. Его отсутствие даёт
`SKIP`, как отсутствующий CLI в диагностике — маршрут недоступен, проект не
сломан.

Проверка детерминизма стоит второй конвертации, то есть удваивает время и
место. Это названо в skill и снимается флагом `--skip-determinism-check`,
который печатает `WARN`: тихо отказаться от гарантии нельзя.

Приёмка разделена по способу проверки. Тестами закрыты: расположение выгрузки
вне репозитория, её удаление после операции и после отказа, детерминизм как
остановка, владение временными каталогами, блокировка и её истечение, показ
изменений до применения, применение показанного, отказ при сдвинутом каноне и
при исчезнувшей выгрузке, отказ при `folder` вне репозитория, отказ при сдвинутом каноне уже после показа,
отказ при символических ссылках, ограничение размера отчёта, чтение cp1251,
поведение CLI и его кодов возврата.
Только текстом skill проверяются гейт XML-маршрута и предупреждение о цене:
машинного исполнителя у них нет. `deploy-1c-source` и `deploy-and-test-1c`
поставлены как порядок действий без исполнителя — дефект №165.

1. Конвертация EDT → XML во временный каталог вне рабочего дерева, абсолютный
   путь для инструментов, гарантированное удаление, включая аварийное.
2. Возврат в канон отдельным шагом с показом diff; отказ при изменившемся
   каноне.
3. `export-1c-source`, `deploy-1c-source`, `deploy-and-test-1c` с фиксацией
   направления, session lock и non-prod по умолчанию.
4. Правило приоритета EDT (решение 1.28) действует в сессии: XML-маршрут
   требует названной причины, предупреждения и подтверждения.

Приёмка: детерминизм конвертации; ветка `designer-xml` конвертацию пропускает;
временный каталог отсутствует после операции и не попадает в рабочее дерево;
молчаливый возврат в канон невозможен.

Ревью: поведение на большой конфигурации (время и место на диске); что
происходит при параллельном запуске двух конвертаций; полнота предупреждения
перед XML-маршрутом.

### Э10. Тесты, документация, готовность

**Выполнен 2026-07-28.** Зависит от всех. Размер: **L**, а не M — матрица на
31 критерий и три новых проверяющих скрипта не укладываются в M.
Ветка `feat/1c-readiness`.

**A. Матрица готовности — ядро этапа.** `docs/quality/READINESS_1C.md`: строка
на каждый критерий готовности мастер-плана со статусом (`тест` / `только
Windows` / `не выполнено`) и доказательством — именем теста, вехой или номером
дефекта. `scripts/test-1c-readiness.py` читает критерии из мастер-плана и
сверяет с матрицей: критерий без строки, ссылка на несуществующий тест или

проверки через месяц описывает прошлое, а не поставку.

**B. Пробелы, которые матрица вскрывает.** Тест-сканер «нет секретов, машинных
путей и имён рабочих баз» — критерий требует именно теста, а не ревью. Измерение
фактически загружаемой цепочки инструкций с учётом импортов. Report-only
проверка внешних ссылок каталога компонентов: недоступность источника не ломает
сборку. Проверка в валидаторе, что номер дефекта не стоит одновременно в `Open`
и в `Fixed` — при планировании этапа нашлись четыре таких записи.

**C. Документация.** `TOOLS.md`: conditional-компоненты отдельными строками
(Node.js и `docx`, Pillow, OpenSpec CLI, `v8unpack`, YAxUnit, standalone BSL
Language Server). `docs/guides/`: работа с preset `1c` и список «вне scope v1»
(CI/CD, миграция из хранилища, SonarQube, АПК, `cfu`) — критерий требует его в
пользовательской документации, а не только в плане. Сверка
`docs/quality/TESTING.md` с фактическим набором тестов.

**D. Статусы.** Обновление плана, `CHANGELOG.md`, `INDEX.md` и дефекты на всё,
что матрица покажет невыполненным.

Заведомо попадают в «не выполнено» и закрываются не здесь: 13 ролей и 13
upstream-команд в проекциях, OpenSpec с четырьмя workflow, прогон YAxUnit, гейт
release по `practices/1c`, обнаружение Docker provider и весь runtime 1С. Это
Э6 (upstream недоступен) и веха W (нужна Windows-машина). Матрица называет их со
ссылкой на дефект или веху; изобретать содержимое вместо них — значит завести
второй канон.

Приёмка (в модели, которая сложилась по факту): у каждого критерия готовности
есть статус и доказательство — тест, отметка вехи W или **записанный дефект**.
Третьего варианта в первоначальной формулировке не было, и без него этап
пришлось бы либо провалить, либо соврать: четырнадцать критериев не выполнены по
причинам, которые не закрываются на этом этапе. Полный прогон CI зелёный на трёх
ОС.

Статус `частично` появился по итогам ревью: без него картина искажалась в обе
стороны — критерий, закрытый наполовину, выглядел выполненным, а критерий с
проверенной половиной — невыполненным.

Ревью: итоговое — соответствие поставки принятым решениям целиком, а не
поэтапно; список фактически принятых остаточных рисков против раздела плана.

Развилка закрыта действием `adapt`: upstream остаётся источником, наш текст
накладывается адаптациями со ссылками на S.5.1–S.5.3, а при изменении upstream
пересборка падает с указанием на изменившийся фрагмент, то есть обновление
нельзя принять не читая. Класс поставки теперь выводится из действия, а не
константой: `template` получает только выход `adapt` с политикой `seed`, потому
что managed-цель сверяется по хэшу и отрисованный плейсхолдер читался бы как
дрейф.

Отдельно снят дефект №196, который делал бессмысленным сам класс `verbatim`:
`.gitattributes` стандарта разворачивал 60 из 161 файла поставки в CRLF при
каждом checkout. Урок записан в [[docs/quality/PLAYBOOK]].

## Порядок и зависимости

```text
Э1 ─ Э2 ─┬─ Э3 ─ Э4 ─ Э6 ─ Э7 ─ Э8 ─ Э9 ─ Э10
         └─ Э5 ────────────┘        W ─────┘
```

Э5 можно вести параллельно с Э3 и Э4 после завершения Э2: он трогает другой
набор файлов. Всё остальное — строгая последовательность.

## Остаётся за рамками

Отложено осознанно, дефектами не считается: пересборка обработки Toolkit для
`managed` (решение 1.16), CI/CD-пайплайн, миграция из хранилища конфигурации,
SonarQube, АПК и автоматизация `cfu` (решение 1.19), Vanessa Automation
(решение 1.18).
